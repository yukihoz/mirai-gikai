# フォーク運用・本家追従ガイドライン

## 1. 目的

「みらい議会@中央区」プロジェクトは、大元のOSSである `team-mirai/mirai-gikai` をベースとしています。
本家リポジトリの改善（新機能、バグ修正、セキュリティアップデート）を継続的に取り込みつつ、中央区独自のカスタマイズを維持・拡張するための運用方針を定めます。

## 2. Git（上流追従）の基本設定

ローカルの開発環境では、常に自身のフォーク元（`origin`）と大元のリポジトリ（`upstream`）の両方をトラックします。

### 2.1 リモートリポジトリの追加
開発を開始する前に、以下のコマンドで大元リポジトリを `upstream` として追加してください。
```bash
git remote add upstream https://github.com/team-mirai/mirai-gikai.git
```

### 2.2 本家の更新の取り込みフロー
定期的に（または本家で重要な更新があった際に）、以下の手順で本家の `main` ブランチの変更を取り込みます。
```bash
git fetch upstream
git merge upstream/main
# コンフリクトが発生した場合は解消し、コミットします
```

## 3. 中央区独自改修の設計ルール

アップデート時のコンフリクト（競合）を最小限に抑え、保守性を高く保つため、以下のルールに従って機能追加・改修を行います。

### 3.1 既存コードの変更は最小限にする
- **環境変数の活用**: ロゴ画像、サイト名、ベースカラーなどの設定値は、可能な限り環境変数 (`.env`) や外部設定ファイルに切り出し、大元のソースコード自体（ハードコードされたテキスト）を直接書き換えるのを避けます。
- **コンポーネントの分離**: 独自の複雑なUIや機能が必要になった場合は、既存のファイルを大きく改修するのではなく、`xxx-chuo.tsx` のような新規コンポーネントファイルを作成し、呼び出し元だけを差し替えるアプローチを取ります。

### 3.2 データベース（Supabase）の変更ルール
- **マイグレーションの追記**: 新しいテーブルやカラム（例: `meeting_body`）を追加する場合は、絶対に**過去のマイグレーションファイルを直接書き換えない**でください。
- 必ず以下のコマンドで新しいマイグレーションファイルを作成し、差分だけを定義して適用します。
  ```bash
  npx supabase migration new add_feature_xxx
  ```

### 3.3 汎用的な機能は本家（Upstream）に還元する
- 今回行った「衆議院・参議院（originating_house）」を「会議体（meeting_body）」へ抽象化するような改修は、他の地方自治体版でも使える**汎用的な改善**です。
- このような「本家にもメリットがある改修」や「バグ修正」を行った場合は、独自のブランチに抱え込まず、積極的に `team-mirai/mirai-gikai` に対して Pull Request（PR）を送ることを目指します。
- 本家に取り込まれることで、自分たちが将来保守しなければならない「独自差分」が減り、運用の手間が大幅に削減されます。

## 4. 運用・タスクの進め方
今後、新しい機能の要望や改修案が出た場合は、まず本ドキュメントの「3. 設計ルール」に照らし合わせ、**「いかに本家との差分を綺麗に保ちながら実現するか」**というアプローチで実装方針を検討・決定するものとします。

## 5. 本家の更新を取り込んだ後の確認事項

本家と挙動を変えている独自差分のうち、**コンフリクトとして表に出ないもの**をここに記録します。本家の更新を取り込んだら、マージが通っても以下を必ず確認してください。新たにこの種の差分を入れたときは、ここに追記します。

### 5.1 一覧キャッシュの延長と、DBエラー時の例外（DB負荷対策）

**背景**: 2026年11月、Supabase（Free プラン・Nano）のメモリ不足でスワップが常態化し、Disk IO Budget の警告が届いた。DB への問い合わせを減らすため、一覧系のキャッシュを10分から1時間に延ばした（`web/src/lib/cache-tags.ts` の `LIST_CACHE_REVALIDATE_SECONDS`）。

**本家との違い**: キャッシュ期間を延ばすと、DBエラーで返した空配列も1時間残ってしまう。これを防ぐため、`web/src/features/bills/server/repositories/bill-repository.ts` の次の関数は、本家と違って**エラー時に空を返さず例外を投げる**。

- `searchBills`
- `countPublishedBillsByTag`
- `findAllTags`
- `findFeaturedBillsWithContents`
- `findBillIdsWithPublicInterview`

呼び出し側のローダーは、例外をキャッシュ関数の外で受けて空・0件に縮退させている（`getInterviewOpenBills` と同じ形）。

**取り込み後の確認**:

1. 上記の関数を呼ぶ箇所が本家で増えていないか検索する。

   ```bash
   git grep -nE 'countPublishedBillsByTag\(|findAllTags\(|findFeaturedBillsWithContents\(|findBillIdsWithPublicInterview\(|searchBills\(' -- web/src
   ```

   2026年11月時点の呼び出し元は、`bills/server/loaders/` の `get-bills-search.ts`・`get-featured-bills.ts`・`get-bills.ts`・`get-bills-by-diet-session.ts`・`get-bills-by-featured-tags.ts` と、`bills/server/utils/to-bills-with-content.ts`。`filter-bills.ts`・`suggest-bills.ts` が呼ぶ `searchBills` は `shared/utils/search-bills.ts` の同名の別関数なので対象外。これ以外の呼び出し元が出てきて、それが「エラー時は空」を前提にしていたら、キャッシュ関数の外で try/catch して縮退させる。放っておくと、本家では空で表示される場面がこちらではエラーページになる。
2. マージで上記の関数が本家の版（`console.error` して空を返す）に戻っていないか確認する。戻っていると、DBエラーの空の結果が1時間キャッシュされる。
3. 本家が `unstable_cache` から `"use cache"` / `cacheLife` に移行した場合は、次のローダーに1時間のキャッシュ期間を設定し直す。
   - `web/src/features/bills/server/loaders/get-bills-search.ts`（検索結果・カテゴリ）
   - `web/src/features/bills/server/loaders/get-featured-bills.ts`
   - `web/src/features/bills/server/loaders/get-featured-tags.ts`
   - `web/src/features/bills/server/loaders/get-interview-open-bills.ts`
   - `web/src/features/meetings/server/loaders/get-meeting-days.ts`、`get-meeting-day.ts`

この差分は本家にも有益な可能性があるので、本家に取り込まれればこの確認は不要になる（3.3 参照）。
